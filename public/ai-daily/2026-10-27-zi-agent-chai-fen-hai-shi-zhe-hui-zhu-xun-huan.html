30 秒版本

The 30-second version

Anthropic 10 月 22 日发了一篇文章,意思很直接:很多企业 agent 里的子 agent(subagent,一个有自己上下文和工具的小 agent,由主 agent 调度)太多了。把它们折回一个主循环,靠 skill 和按需加载的工具来干活,通常质量更好,还更快更便宜。

On October 22 Anthropic published an article with a blunt message: many enterprise agents carry too many subagents (a small agent with its own context and tools, dispatched by a main agent). Fold them back into one main loop that uses skills and on-demand tools, and you often get better quality, lower latency and lower cost.

但这不是「子 agent 过时了」。文章自己列了三种该留的情况:上下文真的塞爆了、需要并行跑且各自要干净的上下文、单个 agent 选不对工具或指令互相打架。它给的做法是:先建 eval(评测集),一次折一个,分数不掉才算数。

It does not say subagents are obsolete. The article lists three cases where you should keep them: the context really is bloated, you need parallel work with fresh contexts, or one agent cannot pick the right tool or gets conflicting instructions. Its method: build evals first, fold one subagent at a time, and keep the change only if the score holds.

另一份独立数据是 Vals AI 10 月 9 日的实验:同样做 50 个全栈 web app,团队版比单 agent 贵 1.8 到 5.1 倍,质量只在一种配置里显著更好。两份材料放一起读,结论比任何一份都稳:先别加 agent,先量。

A separate data point comes from Vals AI on October 9: on the same 50 full-stack web apps, teams cost 1.8x to 5.1x more than a single agent, and quality was significantly better in only one of four configurations. Read together, the two sources give a steadier conclusion than either alone: do not add agents first; measure first.

我读了什么:Anthropic 文章和 GitHub 迁移套件我读到了正文级摘要;Vals 博客读到了完整的结果表。文章里的数字(2 倍快、system prompt 砍 80%、30 到 50 个工具)是 Anthropic 自己给的,没有给实验方法,我没法独立验证。
What I read: I got body-level summaries of the Anthropic article and the GitHub migration kit, and the full results table from the Vals post. The numbers in the article (2x faster, 80% shorter system prompt, 30 to 50 tools) are Anthropic's own and come without methodology, so I could not verify them independently.

文章到底说了什么

What the article actually says

文章作者是 Diane Sarkis,出自 Anthropic 的 Applied AI 团队的观察。背景是:企业做 agent,常见做法是每个团队做一个子 agent,再由平台团队放一个 orchestrator(编排者)在最上面。结果是子 agent 越堆越多,出现这些毛病:

The author is Diane Sarkis, writing from what Anthropic's Applied AI team has seen. The usual enterprise pattern: each team builds its own subagent, and a platform team puts an orchestrator on top. Subagents pile up, and you get these problems:

  • 交接丢信息。子 agent 之间传的是摘要,细节在交接里掉了。文章把「按问题类型拆」比作传话游戏(telephone game)。
  • 子 agent 泛滥。几百个互相重叠的子 agent,没有标准,没有 owner。
  • Frankenprompt。每个团队往 prompt 里加规则,规则打架,口吻不统一。例子:一家公司的客服 agent 里塞了十几个专科子 agent,品牌口吻很难统一,延迟也拖累体验。
  • 评测各管各的。每个团队只优化自己那一块,领导层看到的是被稀释的分数。
  • 慢。文中说有一位客户发现单循环比他们的多 agent 框架快约 2 倍。
  • Handoffs lose detail. Subagents pass summaries to each other and detail drops out. The article compares splitting by problem type to a game of telephone.
  • Subagent sprawl. Hundreds of overlapping subagents, no standards, no owners.
  • The Frankenprompt. Each team adds rules to the prompt; rules conflict and the voice is inconsistent. One example: a customer-facing agent with a dozen specialist subagents, which made an on-brand voice hard to keep and added latency that hurt the experience.
  • Local evals. Each team optimizes its own slice, and leadership sees watered-down scores.
  • Slow. One customer found a single loop ran about 2x faster than their multi-agent harness.

文章的替代方案叫 progressive disclosure(渐进式披露):agent 一开始只看到每个 skill 的短描述,需要时才加载全文;工具也一样,用 tool search 按需加载,而不是一股脑全塞进 prompt。这样一个 agent 可以「很宽」,但每一刻的上下文并不长。

The alternative is progressive disclosure. The agent starts by seeing only a short description of each skill and loads the full text when needed. Tools work the same way: tool search loads them on demand instead of stuffing them all into the prompt. One agent can be broad without carrying a long context at every moment.

文章给了三个理由:一是同一个 agent 看到每一步,能把步骤串起来,比拿到子 agent 回来的摘要更靠谱;二是 Anthropic 说它把 Claude Code 的 system prompt 砍了 80% 以上,一部分靠渐进式披露;三是从 Opus 4.5 起模型能在单个循环里处理更复杂的计划,会自己讲进度、自己检查,很多外部脚手架变成多余。

It gives three reasons. First, one agent that sees every step can connect them, which beats summaries coming back from subagents. Second, Anthropic says it cut the Claude Code system prompt by more than 80% for newer models, partly through progressive disclosure. Third, starting with Opus 4.5, models handle more complex plans inside one loop; they narrate progress and check their own work, which makes some scaffolding redundant.

单循环长什么样

What the single loop looks like

文章推荐的结构很朴素:一个模型、一个上下文窗口,跑一个开放式的工具循环。每一轮模型吐出一批工具调用,harness(外围运行框架)并行执行,把原始结果返回同一个模型。模型答完或者撞到预算就结束。限制放在 harness 里:轮数预算、成本预算、写操作闸门。

The recommended structure is plain: one model, one context window, one open-ended tool loop. Each turn the model emits a batch of tool calls, the harness (the runtime around the model) runs them in parallel and returns raw results to the same model. The loop ends when the model answers or hits a budget. Limits live in the harness: turn budget, cost budget, write gate.

工具设计上文章给了一个数:工具定义超过大约 30 到 50 个,选工具的准确度会下降。所以工具按用户意图分组,而不是一个 API 一个工具,并配合 tool search 延迟加载。

On tool design the article gives one number: tool selection tends to degrade beyond roughly 30 to 50 tool definitions in the prompt. So group tools by user intent rather than one tool per API, and defer loading with tool search.

什么时候还是该留着子 agent

When you should still keep subagents

文章没有把子 agent 一棍子打死。它说该留或该加的三种情况:

The article does not write subagents off. It names three cases to keep or add them:

  • 上下文膨胀。单循环里已经能测到质量因为上下文太长而变差。
  • 并行 + 干净上下文。多个任务可以同时跑,并且每个用完就能丢掉自己的上下文。
  • 选工具困难或指令冲突。一个 agent 总选错工具,或 system prompt 里的规则互相矛盾。
  • Context bloat. You can measure quality dropping because the context got too long.
  • Parallel work with fresh contexts. Tasks run at the same time and each can throw its context away when done.
  • Tool-selection trouble or conflicting instructions. One agent keeps picking the wrong tool, or rules in the system prompt contradict each other.

如果留,文章的建议是:从最简单的模式开始(generator-verifier 或 orchestrator-subagent),并且按上下文拆,不按问题类型拆。好的候选是互相独立的调研路径、接口干净的组件、黑盒验证。每个子 agent 应该只需要系统其余部分的一点点信息,返回一个紧凑的结果。另外它警告了「康威定律式」架构:每个团队一个子 agent,agent 就成了组织架构图的镜像。

If you keep them, the advice is to start with the simplest pattern (generator-verifier or orchestrator-subagent) and to split by context, not by problem type. Good candidates: independent research paths, components with clean interfaces, black-box verification. Each subagent should need little from the rest of the system and return a compact result. The article also warns against Conway's-law architectures, where each team gets a subagent and the agent mirrors the org chart.

跟 Claude Code 里的子 agent 对上号:Claude Code 的子 agent 文件是带 YAML frontmatter 的 Markdown,只有 name 和 description 必填;tools 是白名单,model 可选 sonnet、opus、haiku 等,isolation: worktree 能让它在临时 git worktree 里跑。今天的 Claude Tips 小课会讲怎么写。
Mapping to Claude Code: a Claude Code subagent is a Markdown file with YAML frontmatter, where only name and description are required; tools is an allowlist, model can be sonnet, opus, haiku and others, and isolation: worktree runs it in a temporary git worktree. Today's Claude Tips lesson covers how to write one.

怎么折:四步,一次动一个

How to fold: four steps, one change at a time

第一步,先建 eval。一套端到端的共享评测由中央团队负责,再加每个 skill 各自的小评测,各团队负责。十个 golden example(人工认可的标准样例)就能起步。按 rubric 给最终答案打分;还有 orchestrator 时跟踪路由准确率,折掉之后看是不是调用了对的 skill 或 tool。系统难以重放的话,给关键事件记时间戳,之后能回放成针对性的评测。

Step 1: build evals first. One shared end-to-end set owned by a central team, plus smaller per-skill sets owned by each team. Ten golden examples (human-approved reference cases) are enough to start. Grade final answers against a rubric; while an orchestrator exists, track routing accuracy, and after folding check whether the right skill or tool got used. If the system is hard to replay, record timestamps on key events so you can replay them as targeted evals later.

第二步,先合并。从用得最多的子 agent 开始。紧耦合的专科(互相接着对方输出干活、碰同一份数据、总是一起被调用)是合并候选。如果线上大部分流量是「A 之后跟着 B」,那就把它们合成一个。

Step 2: merge first. Start with the most-used subagents. Tightly coupled specialists (they chain on each other's output, touch the same data, or are called together) are merge candidates. If most production traffic runs A followed by B, make them one.

第三步,把子 agent 变成主 agent 的 tool(过渡)。主 agent 保持对话,调用子 agent 当工具。好处:统一响应格式、主 agent 能对照真实数据校验、给合成步骤的输入更精简、不用重写子 agent,而且顺手得到一个基线分数。只有子 agent 必须直接跟用户说话时才做完整 handoff。遗留问题:每个专科仍有自己的 prompt、owner 和 eval,结果仍是有损摘要,每次调用是一个嵌套循环,增加延迟。

Step 3: call subagents as tools (the intermediate step). The main agent keeps the conversation and calls subagents as tools. Benefits: a shared response schema, the main agent can check against real data, tighter input to the synthesis step, no rewrite of the subagents, and a baseline score for free. Use a full handoff only when a subagent must talk to the user directly. What remains: each specialist still has its own prompt, owner and evals, results are still lossy summaries, and each call is a nested loop that adds latency.

第四步,一次折一个。把子 agent 的 prompt 变成 skill,把它调的 API 变成 MCP 工具,然后在同一套 eval 上比「折」和「不折」。不要只看总分,要看哪些任务翻转了。文章里的例子:折掉一个子 agent 后延迟降了,但一个查送达日期的任务坏了,因为以前是物流专科负责那次调用,折掉后主 agent 没调就直接答了。这个退化在两次运行里只出现了一次,所以每个任务要跑多次。

Step 4: fold one at a time. Turn the subagent's prompts into a skill and its API calls into MCP tools, then compare folded against kept on the same evals. Do not stop at the aggregate; look at which tasks flipped. The article's example: folding one subagent cut latency but broke a delivery-date lookup, because the shipping specialist used to make that call and the main agent now answered without making it. The regression showed up in only one of two runs, so run each task more than once.

这一步我最认同:看翻转的任务,不看均值。均值能掩盖一个关键流程的崩坏。
This is the step I agree with most: look at the flipped tasks, not the average. An average can hide a critical workflow breaking.

独立数据:团队到底值不值

Independent data: are teams worth it?

Vals AI 在 10 月 9 日发了一个对照实验(作者 Katrina Drozdov)。基准是 Vibe Code Bench:50 个全栈 web app,按产品规格做出来,用 Docker Compose 部署,再由浏览器 agent 跑 UI 测试,得分是通过的 UI 测试比例。八种配置,每种只跑一次:两个模型 × 两档推理强度 × 单 agent 或团队。团队版是一个 lead agent 最多同时派五个子 agent,子 agent 不能再派子 agent。

Vals AI published a controlled comparison on October 9 (author Katrina Drozdov). The benchmark is Vibe Code Bench: 50 full-stack web apps built from product specs, deployed with Docker Compose, then graded by browser agents running UI tests; the score is the share of UI tests passed. Eight setups, each run once: 2 models x 2 reasoning efforts x single agent or team. In the team setup a lead agent spawned up to five subagents at once, and subagents could not spawn their own.

几个读法。第一,只有 Sol 的 medium 档团队版显著更好(+7.3 分)。第二,Sol 的 max 档单 agent(89.0%)比它自己的 medium 档团队(84.9%)还高,虽然差距不显著(p=0.08):对 Sol 来说,加推理强度比加团队划算。第三,Opus 最便宜的配置(medium 单 agent,每个 app 4.08 美元,91.5%)和最贵的(max 团队,每个 app 122 美元,93.2%)分数差不多。第四,时间上两家不一样:Sol 的团队在 max 档更快(中位数 27.6 对 38.4 分钟),Opus 的 max 团队更慢(174.1 对 74.7 分钟)。

How to read it. First, only Sol's medium-effort team was significantly better (+7.3 pts). Second, Sol's max-effort single agent (89.0%) beat its own medium-effort team (84.9%), though not significantly (p=0.08): for Sol, more reasoning effort paid off better than a team. Third, Opus's cheapest setup (medium single agent, $4.08 per app, 91.5%) scored about the same as its most expensive (max team, $122 per app, 93.2%). Fourth, runtime differed by model: Sol's teams were faster at max effort (median 27.6 vs 38.4 min), Opus's max teams were slower (174.1 vs 74.7 min).

作者自己的提醒:这是一个基准(web app)、每种配置只跑一次,结论不一定能推广。他们认为适合团队的任务是「能拆成并行部分」的。这跟 Anthropic 文章的「并行 + 干净上下文」是同一条线。
The authors' own caveat: one benchmark (web apps), each setup run once, so the findings may not generalize. They suggest teams fit tasks that split into parallel parts. That is the same line as the article's "parallel work with fresh contexts".

再补一个背景:今年 1 月有篇 arXiv 论文(2601.04748,Xiaoxiao Li,1 月 8 日提交)提出,多 agent 系统可以「编译」成等价的单 agent + skills,用技能选择换掉 agent 间通信,摘要说能明显降 token 和延迟、准确率保持有竞争力。它还报告了一个现象:skill 库超过某个临界规模后,选择准确率不是缓慢下降而是陡降,而且相似 skill 之间的语义混淆比数量本身更要紧。摘要没给具体数字,所以我不引用数字。这对「折回单循环」是个现实提醒:skill 也不能无限加。

One more piece of background: a January arXiv paper (2601.04748, Xiaoxiao Li, submitted January 8) argues a multi-agent system can be "compiled" into an equivalent single agent with skills, trading inter-agent communication for skill selection; the abstract says this can cut tokens and latency substantially while keeping accuracy competitive. It also reports that skill-selection accuracy holds up to a critical library size and then drops sharply rather than gradually, and that semantic confusability between similar skills matters more than raw count. The abstract gives no figures, so I quote none. It is a practical warning for folding into one loop: you cannot add skills forever.

Anthropic 的迁移套件

Anthropic's migration kit

配套的 GitHub 仓库叫 anthropics/single-agent-loop-kit,是一个 Claude Code skill,按「审计、基线、合并、折叠、当 tool、维护」六个步骤文件带你走。注意它自己标明:这是参考实现,不维护,不接受贡献,Apache-2.0 许可。README 还承认:合并和维护步骤、折完的 single_loop/ 版本,以及两个测试任务(t18、t19)没有在真实模型上跑过。

The companion GitHub repo is anthropics/single-agent-loop-kit, a Claude Code skill that walks you through six step files: audit, baseline, merge, fold, as-tool, upkeep. It labels itself a reference implementation that is not maintained and does not accept contributions, under Apache-2.0. The README also admits the merge and upkeep steps, the finished single_loop/ version, and two test tasks (t18, t19) have not been run on a real model.

套件会先审计,让你对每个子 agent 确认结论(折、合并、当 tool、保留),然后一次改一处、跑 eval、对比。每次花钱的运行前它会停下来给 token 估算。README 建议从 10 个任务、2 到 3 次重复开始。它还依赖几个 Claude Code 命令:/claude-api build-eval、hillclimb、prompt-audit、cost-optimize,以及 /skill-creator、/skill-doctor。

The kit audits first and asks you to confirm a verdict per subagent (fold, merge, call as a tool, or keep), then changes one thing at a time, runs the eval, and compares. It pauses before every paid run with a token estimate. The README suggests starting with 10 tasks and 2 to 3 repetitions. It relies on several Claude Code commands: /claude-api build-eval, hillclimb, prompt-audit, cost-optimize, plus /skill-creator and /skill-doctor.

我的怀疑和保留意见

My doubts and reservations

  • 这是厂商视角。文章推荐的正是 Anthropic 自己的 skill、工具和迁移套件。方向我觉得合理,但数字(2 倍快、80%)没有方法说明,别当成通用结论。
  • 跟模型强相关。文章也说,架构建议会随模型进步而变。Vals 的数据里 Sol 和 Opus 对「加团队」的反应完全不同。你换了模型,结论要重测。
  • 没有 eval 就别折。套件作者自己写:没有可重复的 eval,迁移就是「观点问题」。我觉得这是整篇文章最实在的一句。
  • skill 也会泛滥。折回单循环不是消灭复杂度,是把它从「agent 之间」搬到「skill 库里」。1 月那篇论文的临界规模现象说明这里也有上限。
  • 我没查到的:文章里「一个客户 2 倍快」的客户是谁、任务是什么,文章没写;Vals 博客的每组样本只有一次运行。
  • It is a vendor view. The article recommends Anthropic's own skills, tools and kit. The direction seems reasonable to me, but the numbers (2x faster, 80%) come without methodology; do not treat them as general.
  • It depends on the model. The article itself says the architectural advice will shift as models improve. In the Vals data Sol and Opus reacted completely differently to adding a team. If you change models, re-measure.
  • No eval, no folding. The kit's README says without a repeatable eval a migration is "a matter of opinion". I think that is the most practical sentence in the whole piece.
  • Skills sprawl too. Folding into one loop does not remove complexity; it moves it from between agents into the skill library. The January paper's critical-size effect suggests a ceiling there as well.
  • What I did not find: who the "2x faster" customer was and what the task was; the Vals post has one run per setup.

在子 agent 之上分派任务的那一层。

先给短描述,需要时再加载全文,skill 和 tool search 都是这个思路。

tool search
工具定义不一次全给模型,需要时搜索再加载。
handoff 交接
把对话整个交给另一个 agent;文章建议只在子 agent 必须直接跟用户说话时用。
eval 评测集
一组任务加评分办法,用来量系统改动前后的好坏。
golden example
人工认可的标准样例,eval 的起点。
harness
模型外围的运行框架:循环、预算、权限闸门。
subagent
A small agent with its own context, tools and instructions, dispatched by a main agent.
orchestrator
The layer above subagents that assigns tasks.
progressive disclosure
Show a short description first and load the full text on demand; skills and tool search both work this way.
skill
A packaged procedure and set of judgment rules, loaded on demand.
tool search
Tool definitions are not all handed to the model up front; it searches and loads them when needed.
handoff
Passing the whole conversation to another agent; the article suggests it only when a subagent must talk to the user directly.
eval
A set of tasks plus a scoring method, used to measure a system before and after a change.
golden example
A human-approved reference case; the starting point for an eval.
harness
The runtime around the model: the loop, budgets, permission gates.
