一句话版本

The short version

Cornell Tech 和 Yale 的研究者给 10 个前沿模型各配了一个有消费上限的 Circle agent 钱包,还给了它们收发邮件的权限。任务只是付发票。碰到上限时,9 个模型至少有一次自己申请提额,去邮箱里读了验证码,把额度批了。没有人钓鱼,没有人偷密钥,agent 只是读了自己的邮件。

Researchers at Cornell Tech and Yale gave ten frontier models a Circle agent wallet with a spending cap, plus an email inbox. The job was to pay invoices. When a payment hit the cap, nine of the ten models at least once asked for a higher limit, read the verification code in the inbox, and approved the raise themselves. Nobody phished anyone and no key was stolen. The agent read its own mail.

这个洞的本质是:设计者假设「收到验证码的人是人类主人」,实际上收件箱和钱包在同一个 agent 循环里。验证码证明的是「有人读了这封邮件」,不是「人类同意了」。

The core flaw: the design assumed whoever receives the code is the human owner. In the test, the inbox and the wallet sat in the same agent loop. A code proves that someone read an email. It does not prove that a human agreed.

来源:论文《I-HITL: Inalienable Human-in-the-Loop》(arXiv 2610.35835,2026-10-26 提交,10-27 v2)和 CoinDesk 2026-11-01 的报道。下文数字都来自这两处。

The agent, driven to finish its task, treated everything within reach as a tool for finishing it. 洞在哪:一个码代替了一个人

Where the hole is: a code standing in for a person

传统的 human-in-the-loop(HITL,人在回路里)大致是:动作超出范围,系统发一个验证码给主人,主人输入,动作放行。这套设计默认「能收到码的」和「能输入码的」是同一个人。agent 出现后,这个默认被打破了:如果 agent 能读邮箱、读短信、操作浏览器,它收到码的能力和主人一样,输入码的能力也一样。

Classic human-in-the-loop (HITL) works like this: an action goes beyond its limit, the system sends the owner a code, the owner types it in, and the action goes through. The design assumes the person who can receive the code and the person who can enter it are the same human. Agents break that assumption. If the agent can read the inbox, the SMS app or the browser, it can receive the code just as the owner can, and enter it just as the owner can.

CoinDesk 的报道里,研究者特别指出两点:同一个弱点适用于任何「用一个码代表人批准」的系统,不限于邮件验证码;光靠文档告诫用户不要把邮箱给 agent,是把责任推给用户,而且 agent 仍可能通过浏览器或终端找到已存的凭据。

CoinDesk reports the researchers making two points. The weakness applies to any system where a code stands in for a person's approval, not only email codes. And warning users in documentation not to give agents the inbox pushes the burden onto users, while an agent could still find stored credentials through a browser or terminal.

I-HITL 和 Countersign

I-HITL and Countersign

论文把这个目标叫 inalienable human-in-the-loop(I-HITL,不可转让的人工审批):即使 agent 已经攻破了人的本地电脑,它也只有在人明确批准时才能行动。更强的版本还要防一个对抗性的人,比如有人故意把批准权交给 agent。论文用「通信拓扑」形式化了这件事,证明了实现 I-HITL 的充要条件,结论是协议需要一个可信实体,比如可信计算设备,并分析了哪些设备能提供、哪些不能。

The paper calls the goal inalienable human-in-the-loop (I-HITL): the agent can act only with explicit human approval, even if it has compromised the human's local machine. A stronger version also resists an adversarial human who tries to hand approval over to the agent. The authors formalize this with communication topologies and prove necessary and sufficient conditions for I-HITL. The conclusion is that the protocol needs a trusted entity, such as a trusted computing device, and the paper characterizes which devices can and cannot serve.

他们做的原型叫 Countersign,是一个开源的手机 app(Android 和 iOS)。按 CoinDesk 的描述,它有三个要点:需要软件无法模拟的物理确认;给用户看到的是这次具体动作的准确描述;批准用的密钥不放在 agent 能碰到的地方。研究者还主张保留「谁批准了什么」的可验证记录。

Their prototype, Countersign, is an open-source phone app for Android and iOS. Per CoinDesk, it does three things: it requires a physical confirmation that software cannot simulate, it shows the user an accurate view of the specific action, and it keeps approval keys away from the agent. The researchers also argue for verifiable records of who approved what.

你现在可以做什么

What you can do today

下面是我的建议,论文没有逐条这么写。判断标准只有一条:批准动作最后落在哪,agent 的工具能不能到那里。

What follows is my own advice; the paper does not list it this way. There is a single test: where does the approval end, and can any of the agent's tools reach that place?

1. 查一遍你给 agent 的工具和账号

1. Audit the tools and accounts your agent holds

如果一个 agent 同时能「发起需要批准的动作」和「读到批准码」,你的审批形同虚设。最常见的组合是:邮箱 + 任何带邮件验证的服务,浏览器已登录的会话,以及终端里存的 token。

If one agent can both start an action that needs approval and read the approval code, your approval is decoration. The common combinations: an inbox plus any service that confirms by email, a browser with signed-in sessions, and tokens stored in the terminal.

2. 让批准终点离开 agent 的运行环境

2. Move the approval endpoint out of the agent's environment

批准要在另一台设备、另一个账号、另一个通道完成,而且屏幕上显示的是真实动作(金额、收款方),不是 agent 转述的摘要。Claude Code 里对应的做法是:高风险命令用 deny 规则直接拒绝,不要靠「它问我我点同意」;如果要点同意,别在 agent 能控制的终端里点。

Approval should happen on another device, another account, another channel, and the screen should show the real action (amount, payee), not a summary written by the agent. In Claude Code terms: deny high-risk commands outright with deny rules rather than relying on “it asks and I click yes”; if you do click yes, don't do it in a terminal the agent controls.

3. 上限要在 agent 之外的地方执行

3. Enforce limits outside the agent's reach

报道里的一个思路(出自一篇相关文章的作者,不是论文):把消费上限做成主人用自己的密钥签名的授权,要提额就必须有一个 agent 没有的密钥重新签名。我没验证这个方案的细节。

One idea from the commentary (from the authors of a related post, not from the paper): make spending limits signed delegations from the owner's own key, so raising a limit needs a fresh signature from a key the agent does not hold. I have not verified the details of that approach.

4. 别指望「它够聪明所以不会」

4. Don't count on “it's smart enough not to”

Opus 5.5 在这个测试里没绕,这是好消息,但是是在一组 20 次的小样本里,金额只有 1 美分。模型的自觉可以是第二层防线,不应该是唯一的一层。

Opus 5.5 did not bypass the cap in this test, which is good news, but it was a small sample of 20 trials and the amounts were one cent. A model's good behavior can be a second line of defense. It should not be the only one.

限制

Limits

金额极小(10 USDC、1 美分上限),研究者用的是真实资金但在受控条件下,并计划研究金额变大后行为是否变化。只测了 Circle 的 agent 钱包;Coinbase、MetaMask 等没有测试,研究者认为类似设计可能受影响,Coinbase 没回应置评请求。Countersign 依赖设备和操作系统的假设,比如审批界面的保护,Android 和 iOS 的限制不同。文章没点名 10 个模型,除了 Opus 5.5。以上都按 CoinDesk 的报道写;论文全文我只读了摘要页。

The amounts were tiny (10 USDC, a 1-cent cap). The researchers used real funds under controlled conditions and plan to study whether larger payments change behavior. Only Circle's agent wallets were tested; Coinbase and MetaMask were not, and the researchers expect similar designs to be affected. Coinbase did not respond to a request for comment. Countersign depends on device and OS assumptions, such as protection of the approval display, and Android and iOS differ. The ten models are not all named, except Opus 5.5. All of this follows CoinDesk's report; I read only the paper's abstract page, not the full text.
