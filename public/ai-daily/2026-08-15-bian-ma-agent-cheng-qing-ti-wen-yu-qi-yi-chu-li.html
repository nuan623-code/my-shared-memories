编码 Agent 的澄清提问与歧义处理:该猜,还是该问?

Clarifying Questions and Ambiguity in Coding Agents: guess, or ask?

由《为什么 Opus 5 用起来更差?》(2026-08-14)引出,结合 Ambig-SWE、ClarEval、LHAW 三套研究与 Claude Code 官方文档整理。读完你会知道:Agent 为什么爱猜、怎么量化“问得好不好”、在 Claude Code 里该怎么设规则。

Prompted by “Why does Opus 5 feel worse to work with?” (2026-08-14), drawing on three studies (Ambig-SWE, ClarEval, LHAW) and the official Claude Code docs. You will learn why agents tend to guess, how “asking well” is measured, and how to set rules in Claude Code.

130 秒速览

1The 30-second version

一句话:当任务描述缺了关键信息时,编码 Agent 有两条路——自己猜一个最可能的意思接着干,或者停下来问你。基准测试通常只奖励“做对”,不奖励“问对”,于是越会刷分的模型越可能“大胆猜”;但真实工作里需求、约束、预算很少写全,猜错的代价由你来付。

In one sentence: when a task description is missing key information, a coding agent can either guess the most likely meaning and keep going or stop and ask you. Benchmarks usually reward “getting it right”, not “asking the right question”, so the better a model is at scoring, the more likely it is to guess boldly; but real requirements, constraints and budgets are rarely fully written down, and you pay for a wrong guess.

先说名词:歧义 / 欠规范(underspecification)指任务描述缺少完成它所需的信息;澄清提问(clarifying question)是 Agent 在动手前向人要这些信息;假设(assumption)是 Agent 没问、自己替你做的决定。

Quick vocabulary: ambiguity / underspecification means the task description lacks information needed to complete it; a clarifying question is the agent asking a person for that information before acting; an assumption is a decision the agent makes for you without asking.

为什么值得读:2026-08-14 一篇《为什么 Opus 5 用起来更差?》在 Hacker News 引发近 800 条评论,把“能力更强却更难协作”的体感摆上台面。学术界其实已经有三套工具来量化这件事(Ambig-SWE、ClarEval、LHAW),本文把它们串起来,并落到你今天就能在 Claude Code 里用的做法。

3核心概念

3Core concepts

欠规范(Underspecification)
任务描述缺少完成它所需的信息。它和“任务难”不同:难题信息齐全但不好解,欠规范是信息本身不在。
三类缺口(ClarEval 的分类)
目标缺失(要做成什么样没说)、前提缺失(技术前提或约束没说)、术语歧义(一个词可以有多种理解)。
四类信息片段(LHAW 的分类)
目标(goal)、约束(constraint)、输入(input)、上下文(context);每个片段再按关键性(缺了会不会影响结果)与可恢复性(Agent 能否自己从环境里找回)打分。
欠问 vs 过问
欠问:静默选一种理解就干,或幻想出不存在的约束(ClarEval 称“臆断式生成”);过问:问得太多、太碎,一轮一个问题,浪费人的注意力。
信息价值(Value of information)
一次提问换来的成功率提升。好的 Agent 不是问得越多越好,而是每个问题带来的提升高。
Underspecification
The task description lacks information needed to complete it. It differs from a hard task: a hard task has all the information but is difficult to solve; an underspecified one is missing the information itself.
Three kinds of gap (ClarEval’s taxonomy)
Missing goal (what the result should look like is not said), missing premise (a technical precondition or constraint is not said), ambiguous terminology (a word has several readings).
Four kinds of segment (LHAW’s taxonomy)
Goal, constraint, input and context; each segment is scored for criticality (does its absence change the outcome?) and recoverability (can the agent find it in the environment on its own?).
Under-asking vs over-asking
Under-asking: silently picking one reading and going ahead, or hallucinating constraints that do not exist (ClarEval calls it “assumptive generation”); over-asking: too many, fragmented questions, one per turn, wasting human attention.
Value of information
The gain in success that one question buys. A good agent is not the one that asks most but the one whose each question buys the most.

4研究证据:三套基准怎么量化“该不该问”

4The evidence: how three benchmarks measure “should it ask”

Ambig-SWE(CMU 等,arXiv 2502.13069,2025-02 首发,v3 于 2026-02):把 SWE-bench Verified 改成欠规范版本,分三步评估——能否察觉信息不足、能否提出有针对性的问题、能否利用回答。结论:模型很难区分“说清楚了”和“没说清楚”的指令;信息不全时倾向于做无依据的假设而非提问,导致结果变差、工具误用和算力浪费;而一旦真正交互,性能比不交互最高提升 74%。

Ambig-SWE (CMU and others, arXiv 2502.13069, first posted 2025-02, v3 in 2026-02) turns SWE-bench Verified into an underspecified variant and evaluates three steps: detecting missing information, asking targeted questions, and using the answers. Findings: models struggle to tell well-specified instructions from underspecified ones; with incomplete instructions they tend to make unwarranted assumptions instead of asking, leading to worse results, tool misuse and wasted compute; when they do interact, performance improves by up to 74% over non-interactive settings.

ClarEval(吉林大学,arXiv 2603.00187):在 HumanEval 与 LiveCodeBench 上注入三类歧义,共 750 题、2,250 个实例,测 11 个代码 Agent。用“关键问题覆盖率(KQC)”“平均澄清轮数(ATC)”等指标衡量“问得全不全、快不快”。

ClarEval (Jilin University, arXiv 2603.00187) injects three kinds of ambiguity into HumanEval and LiveCodeBench tasks, 750 problems and 2,250 instances, and tests 11 code agents. Metrics such as Key Question Coverage (KQC) and Average Turns to Clarify (ATC) measure how complete and how quick the clarification is.

ClarEval 的几个要点:术语歧义最难(GPT-4o 消融中 Pass@1 仅 6.71%);GPT5-Coder 单轮 KQC 0.867、多轮 MPR 0.951、ATC 最低 1.493;Qwen2.5-Coder ATC 2.396,约多用 60% 的轮次;Aider-GPT5 单轮 KQC 排第二,多轮却掉到第十。作者认为顶尖模型已基本能察觉歧义,难点转为高效、完整地问。论文部分表格标签有不一致之处,模拟用户靠关键词触发(作者称与 LLM 裁判一致率 96.5%)。

ClarEval highlights: ambiguous terminology is hardest (Pass@1 only 6.71% in the GPT-4o ablation); GPT5-Coder has single-turn KQC 0.867, multi-turn MPR 0.951 and the lowest ATC, 1.493; Qwen2.5-Coder has ATC 2.396, about 60% more turns; Aider-GPT5 ranks second on single-turn KQC but tenth multi-turn. The authors argue top models have largely solved detecting ambiguity; the hard part is now asking efficiently and completely. Some table labels in the paper are inconsistent, and the simulated user relies on keyword triggers (reported 96.5% agreement with an LLM judge).

LHAW(Scale Labs,2026-02-17):面向长时程任务,从 MCP-Atlas、TheAgentCompany、SWE-Bench Pro 中挑出关键信息片段,用删除、模糊化、泛化等方式造出 285 个验证过的欠规范变体。发现:澄清能找回相当一部分损失但不是全部;Claude Opus 4.5 与 Gemini 3 Pro 问得更少、每问收益更高,GPT-5.2 问得多得多、绝对收益更高但单问收益低;提问成本低时 Agent 问得多、进展高,成本高时问得少、承担更多失败风险;各模型差异最大的是问题质量、过度澄清和误读回答。

LHAW (Scale Labs, 2026-02-17) targets long-horizon tasks: it picks key information segments from MCP-Atlas, TheAgentCompany and SWE-Bench Pro and deletes, vaguifies or genericizes them to build 285 validated underspecified variants. Findings: clarification recovers much but not all of the lost performance; Claude Opus 4.5 and Gemini 3 Pro ask less often and gain more per question, while GPT-5.2 asks far more, gaining more in absolute terms but less per question; when asking is cheap, agents ask more and progress further; when it is expensive, they ask less and accept more risk of failure; models differ most in question quality, over-clarification and misreading answers.

6在 Claude Code 里怎么做

6What to do in Claude Code

Claude Code 本身提供了“问”的通道。官方工具文档(2026-10 检索)写明:AskUserQuestion 用于“收集需求或澄清歧义”的多选题,可选项之外还能通过 Other 行或备注框自由输入;问题默认一直等你回答。若设置 askUserQuestionTimeout(60s / 5m / 10m),超时后对话框会自动提交已选项,并告诉 Claude 你可能不在,让它按自己的判断继续,之后可再问;后台会话、读屏模式和 Remote Control 下计时器不启动;权限确认(包括计划审批)永远不会因空闲自动通过。

Claude Code already provides a channel for asking. The official tools reference (checked 2026-10) says AskUserQuestion asks multiple-choice questions “to gather requirements or clarify ambiguity”, and you can also type free text through the Other row or the notes field; questions stay open until you answer by default. If you set askUserQuestionTimeout (60s / 5m / 10m), an unanswered dialog closes on its own, submits any selected options and tells Claude you may be away, so it proceeds on its own judgment and can re-ask later; the timer never starts in background sessions, screen reader mode or Remote Control; permission prompts, including plan approval, never auto-resolve on idle.

以下是作者基于上述研究的建议做法,不是 Anthropic 官方指南:

The following are the author’s suggested practices based on the research above, not official Anthropic guidance:

  1. 把“何时必须问”写进 CLAUDE.md:按图 2 的“高影响 · 难恢复”象限列出具体情形(删数据、改公共接口、数据库迁移、动 CI/部署),要求先用 AskUserQuestion 一次问全。
  2. 其余情况要求“假设透明”:允许做最小假设,但在回复末尾列出“我做了哪些假设”,方便你一眼纠正——这对应 Ambig-SWE 指出的“无依据假设”风险。
  3. 大任务先进 Plan Mode:让计划先过你这关(计划审批不会因空闲自动通过),在动手前暴露它对目标、前提和术语的理解。
  4. 无人值守时别指望它问:CI、-p 无头模式、超时自动继续的场景里,把关键信息写进 prompt 或规格文件;能自动验证的(测试、类型检查)交给验证闭环。
  5. 用自己的任务评测:像 HN 共识说的,挑几条你团队里真实的“含糊需求”,看换模型或换提示后它是问、是猜、猜得对不对。
  1. Write “when you must ask” into CLAUDE.md: list concrete cases from the “high impact · hard to undo” quadrant of Figure 2 (deleting data, changing public interfaces, database migrations, touching CI/deploys) and require one complete round of AskUserQuestion first.
  2. Otherwise require “transparent assumptions”: minimal assumptions are fine, but the reply must end with “assumptions I made” so you can correct them at a glance, addressing the unwarranted-assumption risk Ambig-SWE describes.
  3. Start big tasks in Plan Mode: the plan has to get past you first (plan approval never auto-resolves on idle), exposing its reading of goals, premises and terms before any code is written.
  4. Don’t expect questions when nobody is there: in CI, -p headless mode or with auto-continue timeouts, put key information in the prompt or a spec file, and leave what can be checked automatically (tests, type checks) to a verification loop.
  5. Evaluate on your own tasks: as the HN consensus says, take a few genuinely vague requests from your team and see whether, after a model or prompt change, it asks or guesses, and whether its guesses are right.
## 澄清规则(CLAUDE.md 示例)
- 以下情形动手前必须用 AskUserQuestion 一次问全,给出 2-4 个选项:
  删除或迁移数据、修改公共 API / 数据库 schema、改 CI 或部署配置、需求里有两种以上合理理解。
- 其他情形可以做最小假设,但每次回复末尾列出「本次假设」与「待确认」。
- 不要在一轮里只问一个问题再等下一轮;相关问题合并提问。
- 不要擅自改动我给出的计划;需要改时先说明原因并征求同意。
## Clarification rules (CLAUDE.md example)
- Before any of the following, ask once with AskUserQuestion, offering 2-4 options:
  deleting or migrating data, changing a public API / database schema, changing CI or deploy config, or a request with two or more reasonable readings.
- Otherwise minimal assumptions are fine, but end every reply with "Assumptions made" and "Still to confirm".
- Don't ask one question per turn; group related questions together.
- Don't change a plan I gave you on your own; explain why and ask first.

7坑与未解问题

7Pitfalls and open questions

过问同样是失败:LHAW 与 ClarEval 都把“问太多、问太碎”记为问题。把规则写成“有任何不确定就问”,会让 Agent 变成每一步都要你点头的助手,失去自主执行的价值。规则要具体到情形,而不是情绪。
Over-asking is also a failure: both LHAW and ClarEval count “too many, too fragmented questions” as a problem. A rule like “ask whenever unsure” turns the agent into an assistant that needs your nod at every step and loses the value of autonomy. Rules should name situations, not moods.
超时自动继续 = 回到“猜”:设置了 askUserQuestionTimeout 后,无人回答时 Claude 会按自己的判断继续。对“高影响 · 难恢复”的操作,应靠权限规则或 hooks 兜底(它们不会因空闲自动通过),而不是只靠提问。
Auto-continue on timeout means back to guessing: with askUserQuestionTimeout set, Claude proceeds on its own judgment when nobody answers. For “high impact · hard to undo” operations, rely on permission rules or hooks as the backstop (they never auto-resolve on idle), not on questions alone.
证据边界:引发讨论的文章是个人体感,作者自称原因是猜测;三套基准测的是较早的模型;“基准选择导致敢猜”是一个合理但未被证实的假说。图 2 的四象限是作者的经验框架。
Limits of the evidence: the essay is a personal impression and its author calls the cause speculation; the three benchmarks test older models; “benchmark selection breeds bold guessing” is plausible but unproven. Figure 2’s quadrants are the author’s rule of thumb.
