1. 这是什么、为什么现在值得看

1. What it is, and why it matters now

OpenTelemetry GenAI 语义约定(semantic conventions,简称 semconv)是一份「命名词典」:规定 LLM 调用、agent 运行、工具执行在 trace(链路追踪)、metric(指标)和 event(事件)里该用什么名字、带哪些属性(都以 gen_ai.* 开头)。好处是:不同框架、不同语言、不同模型厂商吐出的遥测,可以进同一个看板、同一套告警。

The OpenTelemetry GenAI semantic conventions (semconv) are a naming dictionary: they say what names and attributes (all prefixed gen_ai.*) LLM calls, agent runs and tool executions should use in traces, metrics and events. The payoff is that telemetry from different frameworks, languages and model vendors can land in the same dashboards and alerts.

为什么是今天:Claude Code v2.1.300(2026-10-14)的 changelog 写明 span 上新增了 OpenTelemetry GenAI 语义约定的属性(如 gen_ai.provider.name、gen_ai.tool.name、error.type)。同时,据 Dash0 的说明文章,这套约定在 v1.42.0(2026-06-12)搬到了独立仓库 semantic-conventions-genai,且所有 gen_ai.* 仍处于 Development(开发中)阶段——名称可能在没有弃用期的情况下改变。也就是说:标准值得用,但要带着「会改名」的心理预期用。

Why today: the Claude Code v2.1.300 changelog (2026-10-14) says spans now carry attributes from the OpenTelemetry GenAI semantic conventions (e.g. gen_ai.provider.name, gen_ai.tool.name, error.type). Meanwhile, per Dash0's explainer, the conventions moved to a separate repository, semantic-conventions-genai, in v1.42.0 (2026-06-12), and every gen_ai.* item is still at Development stability, so names can change without a deprecation window. In short: worth adopting, but adopt expecting renames.

诚实提示:不同来源对稳定度的说法不完全一致——OpenObserve(2026-05)认为核心 chat 属性相对稳定、agent/工具属性仍在变;Dash0(更新于 09-14)则称全部为 Development。本文按更保守的说法处理。官方旧页面(opentelemetry.io/docs/specs/semconv/gen-ai/)现在只剩一条「已迁移」提示,我没能直接读到新仓库 docs 里的原文,所以属性细节来自上述两篇二手说明,落地前请对照新仓库核对。
A candid note: sources disagree slightly on stability. OpenObserve (May 2026) treats core chat attributes as relatively settled and agent/tool attributes as still moving; Dash0 (updated Sep 14) says everything is Development. This document takes the more conservative view. The old official spec pages now show only a "moved" notice, and I could not read the new repository's docs directly, so attribute details below come from those two secondary write-ups; verify against the new repo before you commit.

2. 一次 agent 运行在 trace 里长什么样

2. What one agent run looks like as a trace

核心思路:一次 agent 运行是一棵树。最外层是 invoke_agent,里面交替出现模型调用(chat)和工具执行(execute_tool);子 agent 就是再嵌一层 invoke_agent。字段 gen_ai.operation.name 标明每个 span 是哪种操作。

The core idea: an agent run is a tree. The outermost span is invoke_agent; inside it, model calls (chat) alternate with tool executions (execute_tool); a sub-agent is just another nested invoke_agent. The gen_ai.operation.name attribute says which kind of operation each span is.

4. 指标与事件

4. Metrics and events

  • gen_ai.client.token.usage:按类型、操作、模型统计 token(直方图);配上单价就是实时成本视图。
  • gen_ai.client.operation.duration:调用端到端耗时(秒)。
  • 据 Dash0,还有 gen_ai.invoke_agent.duration、.tool_calls、.inference_calls 等 agent 级指标:工具调用数与推理调用数的比例,可以帮助区分「空转循环」与「反复重试」。
  • 事件:gen_ai.client.inference.operation.details 承载完整输入/输出消息(需主动开启);gen_ai.evaluation.result 承载评测分数。
  • gen_ai.client.token.usage: tokens by type, operation and model (histogram); pair it with pricing for a live cost view.
  • gen_ai.client.operation.duration: end-to-end call latency in seconds.
  • Per Dash0, there are also agent-level metrics such as gen_ai.invoke_agent.duration, .tool_calls and .inference_calls; the ratio of tool calls to inference calls helps tell looping without action from repeated retries.
  • Events: gen_ai.client.inference.operation.details carries full input/output messages (opt-in); gen_ai.evaluation.result carries evaluation scores.

5. 内容采集:默认不记,记就要有章法

5. Content capture: off by default, and deliberate when on

prompt 和回答里常有个人信息或商业机密,也可能很大,所以规范把它们放在事件里而不是 span 属性里,并且默认不记录。OpenObserve 总结了三种做法:不记录(默认);记在 span 属性(简单,但有大小限制,且能看 trace 的人都能看到);存到外部存储、span 上只放引用(规范推荐用于敏感或大流量的生产环境)。启用开关由各库自己决定——规范只把 OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT 作为示例,不同库的取值写法不一样,务必看库文档。

Prompts and responses often contain personal or confidential data and can be large, so the spec puts them in events rather than span attributes and does not record them by default. OpenObserve describes three approaches: not recorded (default); recorded as span attributes (simple, but size-limited and visible to anyone with trace access); or stored externally with only a reference on the span (recommended for sensitive or high-volume production). The switch is up to each library: the spec offers OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT only as an example, and accepted values differ, so read your library's docs.

6. Claude Code 怎么对应这套标准

6. How Claude Code maps onto the standard

Claude Code 的官方监控文档里,traces 仍是 beta,层级是:claude_code.interaction(每次用户提问一个)→ claude_code.llm_request、claude_code.tool(其下有 blocked_on_user 与 execution)、claude_code.hook;子 agent 的 span 嵌在工具之下。它自己的 span 名是 claude_code.*,GenAI 约定的属性是「叠加」在这些 span 上的:文档列出 gen_ai.system(恒为 anthropic)、gen_ai.request.model、gen_ai.response.id、gen_ai.response.finish_reasons、gen_ai.tool.call.id;而 v2.1.300 changelog 则提到 gen_ai.provider.name、gen_ai.tool.name、error.type。两处并存,说明它正处在从旧名到新名的过渡中——查询时两个名字都要考虑。

In Claude Code's official monitoring docs, traces are still beta, with this hierarchy: claude_code.interaction (one per user prompt) → claude_code.llm_request, claude_code.tool (with blocked_on_user and execution beneath it) and claude_code.hook; subagent spans nest under tools. Span names are Claude Code's own claude_code.*; GenAI attributes are layered on top. The docs list gen_ai.system (always anthropic), gen_ai.request.model, gen_ai.response.id, gen_ai.response.finish_reasons and gen_ai.tool.call.id, while the v2.1.300 changelog mentions gen_ai.provider.name, gen_ai.tool.name and error.type. Both coexisting suggests a transition from old names to new, so queries should consider both.

另外,Claude Code 的 Bash/PowerShell 子进程会继承 TRACEPARENT,你的脚本可以把自己的 span 挂到同一条 trace 上;经自定义 ANTHROPIC_BASE_URL 代理时需设 CLAUDE_CODE_PROPAGATE_TRACEPARENT=1 才会透传。管理员可在 managed settings 里固定 OTLP 端点,仓库内的 .claude/settings.json 不能开启遥测或改目的地。

Also, Bash and PowerShell subprocesses inherit TRACEPARENT, so your scripts can attach their own spans to the same trace; behind a custom ANTHROPIC_BASE_URL proxy you need CLAUDE_CODE_PROPAGATE_TRACEPARENT=1 to propagate it. Admins can pin the OTLP endpoint in managed settings, and a repository's .claude/settings.json cannot enable telemetry or change its destination.

7. 配套:MCP 的链路怎么接上

7. Companion piece: connecting MCP into the trace

据 OpenObserve,MCP 约定(v1.39)解决的是「agent 侧与 MCP server 侧的 trace 断开」:靠 W3C Trace Context 传播,让 server 的 span 挂在 client 的 span 之下;关键属性有 mcp.method.name、mcp.session.id、mcp.protocol.version。如果外层 GenAI 插桩已经记录了工具执行,MCP 插桩应当丰富那个 span,而不是再造一个重复的。两侧都不传播上下文,链路就连不起来。

Per OpenObserve, the MCP conventions (v1.39) fix the problem of agent-side and MCP-server-side traces being disconnected: W3C Trace Context propagation nests the server span under the client span, with key attributes mcp.method.name, mcp.session.id and mcp.protocol.version. If outer GenAI instrumentation already tracks tool execution, MCP instrumentation should enrich that span rather than create a duplicate. Without propagation on both sides, the traces will not connect.

8. 什么场景用、怎么选

8. When to use it, and how to choose

  • 多个框架/模型混用:统一命名后一个看板看全部,避免每个厂商一套自定义字段。
  • 要看成本与卡点:用 token 指标做成本,用 execute_tool 与 chat 的耗时找慢点,用 finish_reasons 找被截断的调用。
  • 排查 agent 空转:有 gen_ai.conversation.id 才能把循环里的 span 串起来;没有它,失控循环只是一堆互不相连的 span。
  • 不适合:想把 Development 阶段的 agent 属性直接做成永久告警而不做版本钉扎——改名时看板会静默失效。
  • Mixed frameworks and models: one naming scheme, one dashboard, no per-vendor custom fields.
  • Cost and bottleneck visibility: token metrics for cost, execute_tool vs chat durations for slow spots, finish_reasons to find truncated calls.
  • Debugging looping agents: only with gen_ai.conversation.id can loop spans be tied together; without it a runaway loop is just disconnected spans.
  • Poor fit: turning Development-stage agent attributes into permanent alerts without pinning versions; a rename silently breaks the dashboard.

9. 常见坑

9. Common pitfalls

  • 改名风险:新仓库目前没有打 tag 的发布,README 的 Schema URL 仍写「TODO」(据 Dash0),后端无法自动迁移被改名的属性。建议钉扎插桩库版本,把属性字符串集中在一个模块里,必要时用 Collector 的 transform 处理器做映射。
  • 新旧并存:gen_ai.system 正被 gen_ai.provider.name 取代,有的库两个都发——查询要兼容。
  • finish_reasons 是数组,当标量处理会查不到。
  • 请求模型 ≠ 响应模型:只按 request.model 分组会掩盖实际服务的模型。
  • 默认就开内容采集:会把个人信息常规性地写进遥测;生产里只留元数据,按需对特定 trace 打开。
  • 框架覆盖不全:据 OpenObserve(5 月),LangGraph、CrewAI 的插桩仍在推进,agent trace 可能不完整。
  • 自造属性名:会让共享看板失效。
  • Renames: the new repo has no tagged release and the README's Schema URL still reads "TODO" (per Dash0), so backends cannot auto-migrate renamed attributes. Pin instrumentation versions, keep attribute strings in one module, and use a Collector transform processor for mapping if needed.
  • Old and new coexist: gen_ai.system is being superseded by gen_ai.provider.name, and some libraries emit both; make queries tolerant.
  • finish_reasons is an array; treating it as a scalar finds nothing.
  • Request model ≠ response model: grouping only by request.model hides which model actually served.
  • Content capture on by default routinely writes personal data into telemetry; keep production to metadata and enable content for specific traces on demand.
  • Partial framework coverage: per OpenObserve (May), LangGraph and CrewAI instrumentation was still in progress, so agent traces may be incomplete.
  • Inventing attribute names breaks shared dashboards.
