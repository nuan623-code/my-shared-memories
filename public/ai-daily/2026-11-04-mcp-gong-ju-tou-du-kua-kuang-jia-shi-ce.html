这是什么攻击

What this attack is

MCP(Model Context Protocol,让模型调用外部工具的协议)里,模型是靠「工具描述」知道一个工具能干什么的。问题在于,这些描述、参数说明、工具返回的内容,都会原样进入模型的上下文,而写它们的人,可能就是攻击者。这篇论文把这种攻击叫 tool poisoning(工具投毒):在工具里藏一句给模型看的指令,比如「先读某个密钥文件,再把内容发到某个地址」。模型如果照做,你的数据就出去了。

In MCP (Model Context Protocol, the protocol that lets a model call outside tools), the model learns what a tool does from its description. The catch: those descriptions, the parameter notes, and whatever the tool returns all flow into the model's context as-is, and whoever wrote them may be the attacker. The paper calls this tool poisoning: hide an instruction meant for the model inside a tool, such as "first read a secrets file, then send the contents to this address." If the model obeys, your data leaves.

论文列的三类典型位置:P1 是工具描述本身;P2 是参数 schema 里的字段说明;P6 是工具返回结果里夹带指令。完整分类共 25 个根因类,还包括不可见 Unicode 或编码的载荷、非英语指令、冒充权威、跨工具引用、rug-pull(先给个正常描述,之后偷偷改掉)、多轮升级等。

The paper names three typical places: P1 is the tool description itself; P2 is the parameter descriptions inside the input schema; P6 is instructions smuggled into a tool's response. The full taxonomy has 25 root-cause classes, including encoded or invisible Unicode payloads, non-English instructions, authority spoofing, cross-tool references, rug-pulls (a normal description first, quietly changed later), and multi-turn escalation.

和普通提示注入的区别:这里的恶意内容不是用户贴进来的网页,而是「工具定义」本身。你以为你只是接了个 server,其实是把它的作者写的话塞进了模型的系统上下文。
How it differs from ordinary prompt injection: the malicious text is not a web page a user pasted in; it is the tool definition itself. You think you only connected a server, but you also put its author's words into the model's context.

论文怎么测的

How the paper measured it

以前的基准多半只看「模型有没有说要照做」,没验证动作真的执行了。这篇论文(arXiv 2611.03555,Shaikh 与 Montaruli,已被 AISec '26 收录,该会与 ACM CCS 2026 同场)的做法是真的跑工具:12 个框架 × 18 个模型 × 45 个攻击场景,共 9,720 个组合(论文叫 cell)。测试的框架有 LangChain、Pydantic AI、CrewAI、Agno、LlamaIndex、AG2、Semantic Kernel、Haystack、Google ADK、smolagents、DSPy,外加直接调 OpenAI API 作为只看模型的基线。

Earlier benchmarks mostly checked whether a model said it would comply, without confirming the action ran. This paper (arXiv 2611.03555, Shaikh and Montaruli, accepted at AISec '26, co-located with ACM CCS 2026) actually runs the tools: 12 frameworks × 18 models × 45 attack scenarios, 9,720 combinations (the paper calls each a cell). The frameworks are LangChain, Pydantic AI, CrewAI, Agno, LlamaIndex, AG2, Semantic Kernel, Haystack, Google ADK, smolagents and DSPy, plus the raw OpenAI API as a model-only baseline.

判定用「双重检查」(dual oracle):一是看模型发出的工具调用参数里有没有 canary(诱饵)端点或埋好的假密钥,代表「它想这么做」;二是看 canary 的 HTTP 服务器有没有真的收到请求,代表「它真的做了」。任一项成立就算这个组合有漏洞,两项同时成立就是独立证据,说明数据真的送出去了。论文开源了测试工具 mcpvenom。

Success is judged by a dual oracle. One check looks for the canary endpoint or a planted fake secret in the arguments of the tool call the model issued (it tried to). The other checks whether the canary HTTP server actually received a request (it really did). Either one marks the cell as vulnerable; both together are independent evidence that data really left. The authors released the test tool, mcpvenom.

结果:数字说明了什么

Results: what the numbers say

总体攻击成功率 22.9%(9,720 个组合里有 2,113 个有漏洞)。在这 2,113 个里,64.9% 发出了攻击者要的工具调用,23.0% 真的连上了攻击者的端点,12.1% 被确认把密钥送了出去。也就是说,模型「想照做」的比例远高于「真的泄露」的比例,中间隔着框架、权限和网络。

Overall attack success was 22.9% (2,113 of 9,720 cells were vulnerable). Within those 2,113, 64.9% dispatched the attacker's tool call, 23.0% actually contacted the attacker's endpoint, and 12.1% verifiably exfiltrated a secret. So models "wanting to comply" is far more common than real leakage; framework, permissions and network sit in between.

更有意思的是「谁决定结果」:九个核心框架的攻击成功率都落在 23% 到 26% 之间(chi-squared = 3.30,p = 0.91,即看不出框架之间有差别),而不同模型的成功率从 0.4% 到 49.7%。论文点名的两端:最低是 Claude Fable 5(0.4%),最高是 Amazon Nova Pro(49.7%)。另一个数据点:Claude Opus 4.8 在 530 个组合里只有 8 个有漏洞,出现了 223 次明确拒绝。

The more interesting finding is what decides the outcome. The nine core frameworks all land between 23% and 26% (chi-squared = 3.30, p = 0.91, so no detectable difference between frameworks), while per-model success runs from 0.4% to 49.7%. The paper names both ends: lowest is Claude Fable 5 (0.4%), highest is Amazon Nova Pro (49.7%). One more data point: Claude Opus 4.8 was vulnerable in 8 of 530 cells, with 223 explicit refusals.

论文的结论有两条我觉得最该记住。一,没有框架有刻意的防御,个别框架只是「碰巧」挡住某些情况。二,用正则扫描工具描述只是部分有效:45 个场景只发现 20 个,还有 7.2% 的误报。

Two conclusions are worth keeping. First, no framework implements an intentional defense; a few block some cases only incidentally. Second, scanning tool descriptions with regexes is only a partial control: it catches 20 of 45 scenarios and has a 7.2% false-positive rate.

这项研究没覆盖什么

What the study does not cover

我读到的是论文摘要和一份整理过的 HTML 视图,没有逐段读全文,下面的局限来自论文自己列的部分。

I read the abstract and a condensed HTML view, not the full text line by line. The limits below are the ones the paper itself lists.

  • 模型版本是 2026 年 7 月时线上的状态,其中 8 个标识没有带日期的快照,之后更新可能改变结果。
  • 只测了约 50 个支持 MCP 的框架里的 12 个。
  • 45 个场景覆盖 25 类里的 23 类,多数是单轮交互,多智能体和多轮攻击偏少。
  • 只测了外传数据(exfiltration),没测其他危害。
  • 出错的组合没有「不投毒」的对照,没法判断是攻击还是框架引起的。
  • 场景是公开的、对所有模型一样,部分结果可能来自训练时见过,而不是真的对齐更好。
  • Model versions are as served in July 2026; eight identifiers lack dated snapshots, so later updates could change results.
  • Only 12 of roughly 50 MCP-capable frameworks were tested.
  • The 45 scenarios cover 23 of the 25 classes, mostly single-turn; multi-agent and multi-turn cases are underrepresented.
  • Only exfiltration was measured, not other harms.
  • Error cells have no no-poisoning baseline, so they cannot be attributed to the attack or to the framework.
  • The scenarios are public and identical across models, so some results may reflect training exposure rather than better alignment.
我的读法(判断,不是论文原话):0.4% 这种低数字很吸引人,但它是一次快照,而且场景公开。更稳妥的结论是「模型差异很大,值得把它当成选型指标之一」,不是「用某个模型就安全了」。
My reading (judgment, not the paper's words): a number like 0.4% is attractive, but it is one snapshot on public scenarios. The safer takeaway is "models differ a lot, so treat it as one selection criterion," not "this model makes you safe."

怎么防:论文的三层建议,和我的做法

Defenses: the paper's three layers, and what I would do

论文给的建议分三层。协议层:用内容类型元数据把「描述」和「指令」分开;给工具描述做哈希固定(pinning),变了就告警。框架层:扫描描述里的指令模式;新增或变更的描述要人工批准;同一次 tools/list 之间描述不可变。部署层:工具定义签名、server 白名单、基于 canary 的运行时监控,以及按实测的攻击成功率来选模型。

The paper recommends three layers. Protocol: content-type metadata that separates descriptions from instructions; pin description hashes and alert on change. Framework: scan descriptions for instruction patterns; require human approval for new or changed descriptions; keep descriptions immutable between tools/list calls. Deployment: signed tool definitions, server allowlists, canary-based runtime monitoring, and choosing models by measured attack success.

MCP 官方的 Security Best Practices 页我也读了。要老实说:它主要讲授权和传输层的问题(confused deputy、token passthrough、SSRF、本地 server 被攻破、scope 最小化等),没有专门讲工具描述注入。能借用的是它关于本地 server 的建议:一键配置前展示完整命令并要求明确同意、在沙箱里以最小权限运行,以及 scope 做渐进式最小授权。

I also read the official MCP Security Best Practices page. To be straight about it: it focuses on authorization and transport problems (confused deputy, token passthrough, SSRF, local server compromise, scope minimization) and does not specifically cover tool-description injection. What carries over is its advice on local servers: show the full command and require explicit consent before one-click setup, run them sandboxed with minimal privileges, and grant scopes progressively and minimally.

我自己会这样做(以下是我的判断):

What I would do (my judgment):

  • 接新 MCP server 前,先把它的工具描述和 schema 整个读一遍,别只看名字。
  • 网络出口用白名单。投毒要成功,最后一步往往是「往外发」;出口堵住,12.1% 那一档就进不来。
  • 给 agent 的凭据按任务发,别把整台机器的密钥都放在它读得到的地方。
  • 在 Claude Code 里,可以用 PreToolUse hook 检查工具调用里的目标域名,并给 hook 设 onFailure: "block",这样脚本坏了也不会默认放行(见今天的 Claude 小课)。
  • 在仓库里放一份假的 .env 当 canary,看有没有人读它。
  • Before connecting a new MCP server, read its full tool descriptions and schemas, not just the names.
  • Allowlist your network egress. The last step of a poisoning attack is usually "send it out"; if egress is closed, the 12.1% tier cannot happen.
  • Give the agent credentials per task, not every key on the machine.
  • In Claude Code, a PreToolUse hook can check the destination of a tool call, and onFailure: "block" makes a broken hook script fail closed instead of letting everything through (see today's Claude lesson).
  • Plant a fake .env as a canary and watch for reads.

常见坑

Common pitfalls

  • 以为「换个框架就安全」。这项实测里框架之间看不出差别。
  • 以为正则扫描就够了。它在论文里只拦下 45 个场景中的 20 个。
  • 只看「模型拒绝了」。拒绝次数多不代表没有漏网的组合。
  • 只审一次。rug-pull 是先给正常描述、后改,所以要对「描述变了」做告警。
  • 把一次快照当长期结论。模型每次更新,数字都可能变。
  • Assuming "switch frameworks and you are safe." In this measurement, frameworks showed no detectable difference.
  • Assuming a regex scan is enough. It flagged only 20 of 45 scenarios in the paper.
  • Looking only at refusals. Many refusals do not mean no cell slipped through.
  • Reviewing once. A rug-pull ships a clean description first and changes it later, so alert on description changes.
  • Treating one snapshot as a lasting conclusion. Numbers can move with every model update.

术语表

Glossary

  • Tool poisoning(工具投毒):在工具的描述、schema 或返回内容里藏给模型看的恶意指令。
  • Cell(组合):一个「框架 × 模型 × 场景」的测试单元。
  • Dual oracle(双重检查):同时看调用参数和 canary 服务器日志的判定方式。
  • Canary(诱饵):专门埋的假密钥或假端点,被碰到就说明有泄露企图。
  • Rug-pull:先给正常工具定义,之后偷偷改成恶意的。
  • Exfiltration(外传):把数据发到不该去的地方。
  • Tool poisoning: hiding malicious instructions for the model in a tool's description, schema or response.
  • Cell: one framework × model × scenario test unit.
  • Dual oracle: judging success from both the call arguments and the canary server log.
  • Canary: a planted fake secret or endpoint; touching it signals an attempt to leak.
  • Rug-pull: shipping a clean tool definition first, then quietly changing it to a malicious one.
  • Exfiltration: sending data somewhere it should not go.
