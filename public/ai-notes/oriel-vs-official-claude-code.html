01结论:一句话

官方在 2026 年 4 月把桌面端重做了一遍,那一次重做吃掉的正是这个 app 的主线,而不是它的支线。

这个 app 原本押的三件事——把本机所有 session 收进一块看板、把高风险操作收进一个审批台、用内嵌终端直接托管 session。 一年后回头看:

  • 第三件已经基本没有意义了。官方桌面 app 现在有多 session 侧边栏、每 session 自动 git worktree 隔离、 集成终端与文件编辑器、分屏、应用预览窗格、diff 审阅。这些正好是规划里的阶段 5 / 7 / 10。
  • 第一件被砍掉一半,但剩下的一半是硬的。官方桌面 app 的会话列表只看得见它自己起的 session—— 终端 CLI 里跑的、VS Code 扩展里跑的,一律不进列表。这一条写在官方文档里,不是我推的。
  • 第二件基本完好。官方的权限审批是「一次一弹、弹在那个 session 里」; 没有跨 session 的聚合收件箱、没有风险分级、没有决策留痕、没有按事件类型分档的通知开关(最后这条官方文档明说没有)。

最贵的一条发现

这个项目在 2026-08-08 做过一次同类核查,当时的结论是「手机远程批准和多 session 并行不能再当卖点」。 但那次只核了 Remote Control(手机线),没核桌面 app 的 Code tab—— 而桌面重做在那之前将近四个月就已经发布了。也就是说,那次核查保住了手机线的判断,却漏掉了对 Mac 主线杀伤最大的那一块。 这不是信息不够,是核查范围划错了。

下面是逐条的账。分级用三档:已被替代 部分重叠 仍然独占。

02怎么核的,以及什么不算证据

清单的左半边(自研功能)取自项目自己的功能矩阵文档的 macOS 列,加上执行位置派发方案里的四条,共 48 条。 这是项目内部的唯一权威表,所以不存在「挑对自己有利的功能来比」的问题。

右半边(官方能力)只认三种证据,按可信度排:

  1. 官方文档原文(code.claude.com/docs)——本文的判定绝大多数落在这一档,涉及功能边界的地方直接引原文。
  2. 官方发版说明与主流媒体报道——用来确认「什么时候发的」,不用来确认「具体能做什么」。
  3. 官方 issue 追踪器上的公开状态——只用来确认「某能力还没有」,这是比文档没写更强的证据。

三条自律

一、「文档没写」不等于「不存在」。凡是判「仍然独占」的,本文都说清楚是「文档中查不到对应物」, 而不是断言官方做不到。
二、自研这边的交付状态没有重测。哪条已交付、哪条只在规划里,一律照项目文档的记录,没有实际跑一遍。
三、能力对等不等于体验对等。官方有一个功能,不代表它在这个场景里好用。 但「体验更好」是个需要用户验证的假设,不能拿它给重叠度打折——所以本文一律按能力判,不按手感判。

03官方 2026 年干了什么

按对本项目的杀伤力排,而不是按发布顺序。

① 桌面端重做(2026-04-14)——杀伤力最大的一次

官方把 Claude 桌面 app 的 Code tab 重做了:多 session 侧边栏、拖放式面板布局、集成终端与文件编辑器、 扩展的预览窗格、独立快捷键的侧边对话。官方文档里逐条能查到的有:

  • 侧边栏可按状态 / 项目 / 环境筛选,并可按项目分组;
  • Git 仓库下每个 session 自动分到独立 worktree,默认落在 <project-root>/.claude/worktrees/, 可配置位置与分支前缀,还能在 PR 合并后自动归档;
  • 按住 Cmd 点侧边栏可双 session 分屏;
  • 模型选择器旁的用量环同时给出「本 session 的上下文占用」和「本周期的套餐用量」;
  • 开新 session 时可直接选运行环境:本机 / 云端 / SSH 远程机器 / WSL;
  • 任务面板可看本 session 内的子 agent、后台 shell 命令、动态工作流;
  • 应用预览 + 外部站点浏览 + diff 审阅 + PR 状态监控。

② 手机推送与远程答权限(2026-04-16)

Remote Control 把本机 CLI/VS Code session 连到 claude.ai/code 与手机 app。关键的两句官方原文:

/config 里可开启 Push when actions required,用于「permission prompts and questions」; 且「Claude Code keeps permission prompts and AskUserQuestion questions open until you answer them」。

也就是说,手机上批准权限、手机上回答选择型提示,官方都已经免费提供。 连「连续答了几次权限提示后,CLI 弹一句『Approve tool calls from your phone』」这种细节都有了。

③ Dispatch(手机发任务 → 本机开 session)

在手机上给 Dispatch 发一句任务,它自己判断这是不是开发工作,是就在你的桌面 app 里开一个 Code session, 侧边栏上打 Dispatch 徽标,完成或需要你批准时推你手机。这几乎是自研规划里「手机端派工 + 审批推送」的原样。

④ 跨会话消息与自动分诊

桌面 app 里可以让 Claude「列出我其它的 session、读它们在干嘛、给它们发消息、重命名或归档它们」。 更贴近自研阶段 7 的是:Claude 发现当前任务外值得修的东西时,会给出一个任务卡片,点一下就在新 session + 新 worktree 里开工—— 这就是分诊 + 派工。

⑤ 定时任务与 Routines

三档:CLI 的 /loop、桌面端定时任务(本机跑、最短一分钟、能读本地文件)、云端 Routines(云上跑、最短一小时、无本地文件)。 「每天早上生成一份日报」这种活,官方现在自带。

05逐条对账 · 审批

这是唯一一块越查越站得住的。官方把「远程批准」做透了,但没做「审批台」。这两件事不是一回事。

自研功能判定官方对应物依据 / 备注
跨 session 聚合审批收件箱 仍然独占 文档中查不到 官方的权限提示是 session 内的交互;Dispatch 会在「需要批准」时推手机,但推的是那一个 session。没有把多个 session 的待批请求收进一处的界面。
三级风险分级 + 影响说明 + 人话解释 仍然独占 文档中查不到 官方的权限模式(Manual / Accept edits / Plan / Auto / Bypass)分的是自主程度,不是单条请求的风险。Auto 模式有「后台安全检查」,但那是模型侧判断,不是给用户看的分级。
审批记录(六字段,可回顾)+ 只增不改的审计日志 仍然独占 文档中查不到 企业向的场景里,这一条比收件箱本身更值钱。
按事件类型分档的推送开关(等批准 / 高风险 / 等输入 / 出错 / 完成) 仍然独占 官方明说没有 官方文档原文:「Claude decides when to push… Beyond the two on/off toggles below, there is no per-event configuration」。两个开关分别是「Push when Claude decides」和「Push when actions required」。这条差异在 8-08 那次核查里已经识别过,一年后依然成立。
高风险无一键批 / 无批量批 / 须展开完整详情 仍然独占 不适用(是产品立场) 官方的方向恰好相反:Auto 模式主打「减少权限提示」。这构成真实的定位差异,但要说清它是立场不是功能。
Approve Once / Deny / Deny with Feedback 已被替代 权限提示本身 + 手机远程作答 官方连「保持提示打开直到你回答」的语义都写进文档了。
Allow for This Session(会话级长效授权) 已被替代 权限模式 + 允许规则 + 每目录记忆 官方的模式选择还能按文件夹记住。
Deny and Stop(中断) 已被替代 拒绝 + 中断当前轮 —
选择型提示(问答类)作答 已被替代 官方支持远程回答此类提示 值得单独说:自研这边把「远程回答选择型提示」定成了红线不做;官方直接做了,而且做在手机上。这一条上,官方比自研更激进。
外部 session 的批准操作 已被替代 Remote Control 本次对账里最反直觉的一条。自研这边因为架构限制,对外部 session 一律只读、审批不生效;而官方的 Remote Control 恰恰让终端里的 session 可以远程批准——代价是必须显式开启(跑 claude remote-control),且转录会存到 Anthropic 服务器。

这一节的净结论

审批这块的差异是真的,而且是这份对账里唯一没有被时间稀释的一块。但它的表述必须精确: 不是「官方不能远程批准」(能,而且免费),而是「官方没有把待批请求聚合成一个带风险分级和留痕的台子」。 这两句话的市场含义差得很远——前者已经是假话,后者仍然是真话。

Kitty 形象(静态 + 动态状态机) 仍然独占 不适用 —

08三条卖点,逐条复检

项目的上线 spec 里定了三条卖点。一年后逐条过:

卖点 1 ·「零配置、被动看全部」成立

而且比当初更成立。当初这条的对手是 Remote Control 的「必须显式开启」; 现在多了一个更强的论据:官方自己的桌面 app 也看不见终端里的 session,而且这是写在文档里的已知边界。 一个开着五个终端窗口跑 Claude Code 的人,在官方桌面 app 里看到的是空的。

文案该怎么改

原文案说的是「机器上所有 Claude Code session 自动进看板」。建议加一句更锋利的对照: 「包括官方桌面 app 自己看不见的那些」——这句有官方文档背书,是可以直接核的事实,不是营销话术。

卖点 2 ·「审批收件箱,带风险分级」成立,但表述必须收紧

核过一圈,官方确实没有聚合、没有分级、没有留痕、没有分档通知。但「远程批准」本身早已不是差异点, 且官方在选择型提示远程作答这一项上比自研更激进。所以这条卖点的边界要重画: 卖的是「批之前你看得见多少 / 批之后留下什么」,不是「你能不能在别处批」。

卖点 3 ·「数据通路上没有第三方服务器」半成立

这条当初的依据是 Remote Control 会把转录存到 Anthropic 服务器。那依然是事实。 但它现在只对一小撮人成立——同时满足「在意转录出本机」且「不使用官方桌面 app」的人。 而官方桌面 app 的本机 session 本来就在本机跑。这条更适合作为隐私页的一段说明,而不是首页的第三块 hero。

更值钱的是当初那张限制表里的人群,它们一条都没过期:用 API key 的、走企业 LLM 网关的、 关了遥测的、有零数据留存合规要求的、组织没开 Remote Control 的。这不是卖点,这是 ICP。

09那个盲点:为什么上次没查出来

这一节不讲产品,讲方法,因为它是这次对账里唯一可以复用的东西。

2026-08-08 那次核查做得其实很扎实:拉了官方文档原文、推翻了两份互相打架的二手研究、 逐条列出了 Remote Control 的八条硬边界、并据此砍掉了两句已经站不住的卖点。方法没问题,范围错了。

错在哪

那次核查的入口问题是「官方的手机方案能不能替代我们的手机方案」, 于是查了 Remote Control、Dispatch、Channels、Scheduled tasks——手机线相关的全查了。 但桌面端重做(4 月 14 日发布,比那次核查早了将近四个月)不在这个问题的射程内, 因为它不是手机功能。而它恰恰是对 Mac 主线杀伤最大的一次投放。

可以复用的教训是:竞品核查的范围应该按「对手的产品线」划,不是按「我这次担心的那条线」划。 担心手机被替代,就只去查手机;结果桌面被端了四个月都不知道。

配套的一条:这类核查要定期重跑,而不是立项时跑一次。 从 4 月到 8 月这四个月里,官方发的东西改变了本项目至少 18 条功能的性质,而项目文档里没有任何一处反映这件事。

10还有一件事:这块地已经不空了

对账做到一半发现了一个不在原计划里的问题:「跨品牌 + 菜单栏 + 监控 session」这个位置,已经有人在了。

工具它做什么与自研的关系
so-agentbar从菜单栏追踪每一个活跃的 Claude Code 与 Codex session——CLI、Xcode、桌面 app、Codex 都算,显示 token、花费、状态位置几乎重合:跨品牌 + 菜单栏 + 含 CLI session。差别在它是用量视角,不做审批
ClaudeBar菜单栏监控 Claude / Codex / Gemini / Copilot 的配额跨品牌配额,不碰 session 态势与审批
SessionWatcher菜单栏追踪 Claude / Codex / Copilot / Cursor / Gemini 的用量、花费、限流窗口;含桌面小组件;一次性买断 $6.99 起已经在收钱,且定价档位与自研规划的 Pro 档撞了
Happy(开源)手机端远程控制 Claude Code8 月那次核查已识别,免费

这意味着什么

「跨品牌」本身不再是护城河,它是一个已经有三四个玩家的品类。 真正还没被占的位置是这两条的交集:跨品牌 + 审批台(不是用量表)。 上面这些工具全部停在「看用量」,没有一个碰权限请求——因为那需要接 hooks、需要做风险模型、需要处理超时策略, 是个重得多的工程。这恰好是自研这边已经投了最多的地方。

11还剩什么:护城河按含金量排

「独占」有 15 条,但含金量差得很远。判断标准是两条:官方结构上会不会来做,以及已经有没有别人在做。

把这张图翻译成一句定位:

建议的新定位

从「Claude Code 的管理面板」挪到「所有 coding agent 的统一审批台」。

前者在和官方赛跑,而官方在自己的进程里、有全部信息、还比你快; 后者踩的是官方的结构性盲区(它不会去管 Codex),同时又是现有第三方工具全都绕开的那块硬骨头(它们只做用量,不做审批)。

注意这个新定位不需要新功能——阶段 11/12a/13 那条线本来就在往这走。它需要的是停掉另外几件事。

12对路线图的具体建议

按「继续 / 收缩 / 停掉」三档给,每条都对得上前面的判定。

继续投(踩在护城河 1 和 3 上)

  • 阶段 13(opencode 接入) —— 唯一一个能做到「第三方 agent 也能审批」的方向,是护城河 1 和 3 的交点。优先级应该是最高的。
  • 阶段 12b(Codex 审批与托管) —— 同上。等配额窗口期间可以先把 Core 的抽象欠账补掉。
  • 审批台自身的加固(记录、审计、分档通知、风险模型) —— 这是唯一一块越查越站得住的地方,却排在很后面。建议提前。

收缩范围(还有价值,但别再加功能)

  • 内嵌终端 —— 别砍,它是跨品牌托管的载体;但停止往「比官方终端更好用」的方向投入。官方在进程内,这场比不赢。
  • 阶段 Y(执行位置多目标派发) —— 重新审一遍。官方的「本机 / 云 / SSH / WSL」下拉框四月就有了,Y3/Y4/Y5 三格需要重新论证还剩多少增量。Y1/Y2 做的分诊建议引擎可能仍有价值(那是官方没有的判断层),但「把活派到别处执行」本身已经不稀缺。
  • 每日日报 —— 唯一的差异化理由是「数据源包含官方看不见的 session」。围绕这一点写,别当独立功能做。

建议停掉或降级

  • 阶段 10 的浏览器窗格 —— 官方的预览 + 外部站点浏览已经覆盖,而且尚未开工。这是最容易砍的一格。
  • Files & Diff / Tasks 两个 tab(自家 session 部分) —— 官方的 diff 审阅和任务面板更完整。若要做,只做外部 session 的那一半。
  • 手机端 M4/M5(远程终端镜像与输入) —— Remote Control 完整覆盖且免费。手机端要做,做的应该是审批台的手机版,不是终端的手机版。
  • 官网卖点 3 从首页降级到隐私页 —— 理由见第 8 节。

还有一条与功能无关的

「Dispatch」这个名字和官方的功能重名了——官方的 Dispatch 是「手机发任务给桌面 app」。 自研这边的 Dispatch 页是派工分诊。这两个东西面向的场景还挺接近,重名会造成真实的沟通混乱,建议改名。

13没核到的,和可能错的

把这节写在这里,是因为一份对账报告最容易骗人的地方就是它不说自己哪里虚。

  • 「文档中查不到」不等于「不存在」。判为「仍然独占」的 15 条里,绝大多数依据是官方文档没有描述对应能力。 官方产品迭代速度快于文档,这些判定有过期风险,尤其是审批相关的几条。
  • 没有实机验证。本文没有装官方桌面 app 逐项点过一遍,全部依据文档描述。 「文档说有」和「实际好用」之间的差距没有测量。
  • 自研这边的交付状态没有重测。哪条已交付、哪条在规划,照项目文档记录,没跑一遍验证。
  • 第三方工具只做了搜索层面的了解。so-agentbar 等工具没有实际安装试用, 「它是否真能看见 CLI session」这一条只有它自己的宣称,没有独立验证。这条如果错了,影响的是第 10 节的结论强度。
  • 企业侧完全没查。官方的管控台、受信设备、托管设置这几块只扫到标题,没有细看。 如果未来定位往企业走,这块必须单独重做一次对账。
  • 数字有主观成分。48 条的切分粒度、以及「部分重叠」与「已被替代」之间的界线,都由本文自己划。 换个人划,18/15/15 这组数会变。请把它当作量级参考,不是精确测量。

最后一句是给自己的:这份对账的价值不在那三个数字,而在它把一件本来靠感觉的事 ——「是不是被替代了」——变成了一张可以逐行反驳的表。下次该做的不是再感觉一次,是把这张表重跑一遍。
