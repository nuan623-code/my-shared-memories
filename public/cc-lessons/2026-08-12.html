第 8 课:上下文管理——/clear、/compact 与上下文预算

类型:核心工作流 · 上下文窗口是 Claude Code 最稀缺的资源:塞得越满,模型越容易「忘事」和跑偏,费用也越高。本课 4 条技巧由浅入深,把上下文当预算来管。 来源:官方 Best practices · Blink: /clear vs /compact 与会话交接 · HyperDev: 保护上下文让 Claude Code 变强

技巧 1(入门):/context——先看清上下文都被什么吃掉了

管理之前先测量。/context 会显示当前上下文窗口的占用分解:系统提示、工具定义、MCP 服务器、CLAUDE.md、消息历史各占多少。很多人第一次跑才发现:挂了一堆用不上的 MCP 服务器,还没开始干活窗口就没了一大块。

# 会话内随时输入:
/context
# 看三个数:总占用百分比、MCP/工具定义占比、消息历史占比
# MCP 占比高 → 用 /mcp 或 settings 禁用本项目用不到的服务器
# 历史占比高 → 该 /compact 或 /clear 了(见技巧 2、3)

适用判断:每次开始大任务前、感觉模型「变笨」时,先 /context 看一眼再决定动作。

来源:Claude Code Best practices

技巧 2(基础):/clear 与 /compact 分工——换任务用 clear,长任务中途用 compact

两条经验法则:两个不相关任务之间,默认 /clear(彻底清空,最快最干净,不把上一个任务的噪音拖进下一个);同一个长任务做到一半还需要历史,用 /compact(把对话历史压缩成结构化摘要,保留要点、清掉死重)。

# 修完 bug 要去做新功能 → 换任务,直接:
/clear

# 重构做了 2 小时还没完,历史快满 → 压缩但保住关键信息:
/compact focus on the database schema changes and remaining TODOs

/compact 后面跟的自然语言指令是关键:告诉它保什么(「保留 auth 模块的改动结论和测试结果」),压缩质量远好于裸跑 /compact 让模型自己猜。

来源:Blink: /clear vs /compact 、Brainy 对比解读

技巧 3(进阶):别等自动压缩——60% 时主动 compact,理解 microcompact 兜底

Claude Code 在接近上限时会自动 compact,但被动等它有两个代价:压缩发生在最差时机(上下文已被噪音填满,摘要质量差),而且任务会被打断。社区实践的经验值是:占用到 60% 左右就主动 /compact,而不是拖到 95%。另外新版还有 microcompact 机制:自动清理久远的工具调用记录(读文件输出、命令日志这类「过程垃圾」),保留对话本身——这解释了为什么长会话有时「自己瘦身」了。

# 工作节奏建议:
# 1) 大任务开始:/context 确认起点干净
# 2) 每完成一个里程碑:/compact focus on <里程碑结论>
# 3) 见到占用超 60%:不要开新的大改动,先压缩再继续

适用判断:超长重构、批量迁移、多轮调试这类会话必用;短平快任务不用管,做完 /clear 即可。

来源:HyperDev: 保护上下文 、MindStudio: compact 实践

技巧 4(进阶):外置记忆工作流——把状态写进文件,窗口只留「正在干的事」

上下文管理的终极形态是少依赖窗口内记忆:让 Claude 把计划、进度、决策写到磁盘上的 markdown(如 docs/plan.md、docs/progress.md),每个阶段结束更新文件 → /clear → 新会话开头让它先读文件恢复状态。窗口里永远只有「当前步骤 + 必要背景」,而不是全部历史。这也是官方 best practices 里「用文件做工作记忆」与高分社区实践(dev docs / living plans)的共同做法,且天然支持跨天续做和多人交接。

# 阶段收尾时:
「把本阶段的结论、已改文件清单、下一步计划更新到 docs/progress.md」
/clear
# 新会话开头:
「读 docs/progress.md 和 CLAUDE.md,从『下一步计划』继续」

配合第 1 课的 CLAUDE.md(放「永远要知道」的项目事实)分工明确:CLAUDE.md 管恒定事实,progress.md 管任务状态,窗口只管当下。

来源:Claude Code Best practices 、2026 社区实践综述
